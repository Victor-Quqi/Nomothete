# Nomothete 设计

术语一律以 `CONTEXT.md` 为准。本文只记设计决策。

## 立场

其余决策从这几条推出来。

**用户的判断是唯一标准。** 理由见 [`docs/adr/0001-no-built-in-name-quality-standard.md`](./adr/0001-no-built-in-name-quality-standard.md)。客观约束和主观品味分开处理。能不能注册是硬的，好不好听只属于当前这个用户。

**主要信号来自行为。** 用户点了什么，比填表、写理由更要紧。不做入场问卷。Taste Profile 默认不显示，只用来驱动生成和事后可查。

**流畅优先于功能。** 生成要 3 到 10 秒，永远在后台跑，结果流式追加。任何打断用户的配置、确认或填写，都要先证明自己值这个代价。

## 用户看到的流程

1. 写一句项目描述。可以给种子，比如喜欢的现有名字、讨厌的模式、指定的语义场，或者自己已经想到的几个候选。种子就是预先填好的 Verdict。
2. 第一批名字流式出现，每个带着 Rationale。首批横跨多个互不相干的构词策略和语义场，用来撒开方向。方向由用户选出来。
3. 每个名字可以打四档，`▲▲ ▲ · ▼ ▼▼`。默认停在中性档，大多数名字会一直停在那里。用户备注可选。
4. 打过的档立刻影响后台正在补的下一批。已经生成好的不作废。
5. 每个名字旁边直接显示能不能注册、撞名严重不严重。检查是生成流程的一部分。
6. 关掉再打开，进度还在。给项目起名可能横跨几天。

## 架构

### 形态与分发

自托管 Web 应用。`npx` 或 `docker` 一条命令起服务，用户自带 API key。需要给软件项目起名的人全是开发者，跑得起 npx。

TypeScript 全栈。后端要做的事是调 LLM、并发查注册表、维护本地索引，都是 IO 密集而非 CPU 密集，Node 合适。如果本地索引的归一化匹配变慢，再抽成 Rust 原生模块。

SQLite 单文件，和配置、本地索引一样写在数据目录，可导出。数据目录在装成包运行（含 `npx`）时是 `~/.nomothete/`，免得在别的项目目录里起服务时读到、甚至写进那个项目的 `.env`；从源码运行时是当前工作目录。

### 生成

算法提供词料和策略约束，模型负责语义跳跃。LLM 输出同质化的本质是 cold-start 问题，给它一点具体上下文就会消失，算法生成的词料正好提供这点上下文。

已知有效的做法：

**一次只在单一 Strategy 约束下生成。** 绑定到一个具名策略，比如"从冶金学取拉丁词根"。负面指令（"不要用头韵"）有实测被无视。Strategy 是生成约束；用户对着名字和 Rationale 打档。

**要 k 个候选并让模型自报概率，然后取低概率的那些。** 这能缓解 RLHF 造成的向典型答案坍缩。

自报概率和流式追加会打架。要在一批里挑出低概率的那部分，得等整批到齐才能排序，而"结果流式追加"要求每个名字解析完就出现。解法是用绝对阈值当场筛：流里每个元素带着自己的概率到达，超过阈值就地丢弃，不超过就立刻上屏。候选的元素 schema 是 `{name, probability, rationale}`。每批实际上屏的数量不固定。

**普通人设。** "你是世界级品牌策略师"这类提示实测降低多样性。

调高温度不能解决同质化，已有研究明确否定这条路。

### 检查流程

每个候选生成出来就过一遍检查。每个检查项实现同一个接口，自带成本等级和触发时机：
本地 0ms 与免费网络的对每个候选都跑，限速的等到点赞之后。商标检索是付费档，留到 v2。

加一个新检查项就是往数组里塞一个函数，主流程不动。已落地的清单见 README。

本地全量索引是这个项目最难被别人复制的部分。注册表 404 不等于能注册；PyPI 的 `ultranormalize` 目前没有现成工具复现。同一份索引支撑 Publishability 和 Searchability。常见英语真词是搜索灾难，证据是 Go 搜不到，社区被迫发明了 golang 这个词。

### 数据模型

每个候选是一个节点，带 `parentId` 和偏好档位属性。MVP 里 `parentId` 全为空，渲染出来是扁平列表，它已经是一棵深度为 1 的树。之后加衍生或换呈现形式都只改渲染层，数据不用迁移。

偏好是节点的属性。调整档位不移动节点。只有被点赞的节点才展开子节点，树因此天然稀疏，它的形状本身就显示了用户的偏好方向。

前端只做渲染和事件上报，状态全在后端。

### LLM 适配

四种 API 形态：OpenAI `chat/completions`、OpenAI `responses`、Anthropic `messages`、Google `generateContent`。每种可自定义 base URL 和 key。使用结构化输出；上游不支持则失败。地址和模型留空时连 DeepSeek 官方的 `deepseek-flash`。

起名不吃长上下文。中等模型足够。

用 Vercel AI SDK，入口 `createOpenAI({baseURL, apiKey, name})`。`createOpenAICompatible` 默认关闭结构化输出，并把 json_schema 请求降成 `{type:'json_object'}`，与上面的失败策略冲突。Anthropic 与 Google 用对应官方包，传 `baseURL`。Google 鉴权方式（`x-goog-api-key` 头或 `?key=`）要可配，第三方代理往往只认一种。

配置是具名 profile 列表：`id`、`kind`、`baseURL`、`apiKeyEnv`、`model`、`structuredOutput`。`kind` 四选一。能力检测：对 model id 做正则，附一张常见 id 的小静态表，`structuredOutput` 作手动覆盖。默认 `json_schema`。

例外是 DeepSeek 官方端点：它拒收 `json_schema`，每个这样的请求都是 400，只收 `json_object`。所以对它把 schema 写进系统提示、请求 `json_object`，返回结果照样按 schema 校验，对不上照样失败。`structuredOutput` 写 `json_object` 可以把别的端点也这样处理，只对 OpenAI `chat/completions` 生效。

候选用 `streamObject({output: 'array'})` 消费 `elementStream`，元素为上文的 `{name, probability, rationale}`。数量写在 prompt 里，流结束后校验条数。

key 走环境变量。日志不打请求体和 Authorization 头。浏览器可以写 key，永远读不回 key ——
单向流是设置面板能存在的前提，细则见 [`configuration.md`](./configuration.md)。

选型依据与源码出处见 [`docs/research/provider-adapters.md`](./research/provider-adapters.md)。

## MVP

做这些：描述输入与可选种子、多策略并行播种、异步流式追加、候选附带 Rationale、四档打档、偏好画像内部推断但不显示、完整检查流程只注册本地项与免费网络项、本地索引构建、SQLite 持久化、树形数据模型、扁平列表渲染。

不做这些：树的可视化、限速与付费检查项、偏好画像编辑界面、盲测复检。

核心循环是生成、打档、更好的生成。先把这个循环跑通，证明它真的会收敛，再决定用什么形状画树。界面的呈现与交互等后端成型后并行做几个原型，由你来筛。

## 明确不做

- SaaS、多用户、账号系统
- 任何名字质量评分表或后缀黑名单
- 强制冷却期。"好名字一开始常显得很烂"这个现象有证据，如何应对留给用户自己

## 待定

- 界面的呈现与交互（打档控件、视觉风格、树怎么画），等原型

## 验收

基准测试。用真实项目描述作输入，看能否产出隐喻复合、冷僻词根、行业黑话挪用三档的同水准候选。

收敛性测试。对第 1 代和第 3 代的候选做盲评，第 3 代应当明显更受偏爱。

即时判断是验收手段。语料表明第一反应是好名字的劣质预测器（HN："好名字一开始常显得很烂"）。
